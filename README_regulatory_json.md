### Статусы

- 8 BANNED из предоставленного seed. Это **не подтвержденные первичным актом запреты**:
  `primary_basis_required: true`, `verification_status: verified_official_publication`,
  `production_ready: false`. Перечень найден в официальной публикации
  [Роспотребнадзора от 01.07.2021, стр. 4](https://04.rospotrebnadzor.ru/index.php/component/content/article/41-faq/14896-01072021.pdf#page=4).
  Это подтверждение публикации, а не сверка действующего первичного акта.
  В API они дают `attention` с пояснением о непроверенном основании, а не
  безусловный `forbidden`. Медицинские утверждения из публикаций не извлекались.
- 19 PHASE_OUT: основание исключения сверено по официальному приложению к
  [Решению № 84, п. 2, подп. 7(а), стр. 40 PDF](https://docs.eaeunion.org/upload/iblock/765/txjkhhqysqqmwvgazt2db8yxclc0oiju/err_31082023_84_att.pdf#page=40).
  Отдельно указано [Решение № 8](https://docs.eaeunion.org/documents/429/7931/),
  п. 1, подп. а, б, в: документы соответствия, переходное производство и
  обращение до истечения срока годности. Полный текст этого решения при текущей
  проверке недоступен: его дополнительная ссылка имеет `needs_full_text_review`.
  Даты 26/27.02.2027 рассчитаны от 27.02.2024 и 36 месяцев; это отмечено в данных.
  После 27.02.2027 статус не превращается автоматически в запрет товара:
  без даты изготовления и документов API сохраняет `attention`.
- 6 новых E-позиций уже есть в исходном справочнике. Для E243, E423, E1205,
  E1206, E1207 и E1209 добавлена ссылка на п. 2, подп. 7(б), стр. 41 того же PDF.
- 6 предупреждений о красителях: ТР ТС 022/2011, ст. 4, ч. 4.4, п. 18.
  2 предупреждения об источнике фенилаланина: п. 15 той же части.
  Проверено по [официальному тексту, стр. 11 PDF](https://eec.eaeunion.org/upload/medialibrary/9db/TrTsPishevkaMarkirovka.pdf#page=11).
  Исключения для маркировки сохранены в `conditions.exceptions`. Предупреждение
  об ингредиенте не является заключением о нарушении маркировки товара.
- Остальные нормы применения и чистоты сохранены как `reference_only`.
  Наличие в приложении 2 обозначается `PERMITTED_WITH_CONDITIONS`, но не
  подтверждает безопасность конкретного товара: нужны категория, концентрация,
  технологическая функция и соответствующие ограничения из приложений.

Коды распознаются с латинской/кириллической Е, пробелом, дефисом и буквенным
суффиксом. Для статусных правил отключено приблизительное сопоставление.
Неоднозначные `амарант`, `amaranth`, `стевия`, `stevia`, `красный рис`, `red rice`
не становятся синонимами запрещенной/исключенной добавки. E960 (стевиолгликозиды)
не объединяется с листьями и экстрактами стевии.

### Проверяемость каждой нормы

В `ingredient_rules` сохранены адресуемые нормы. `citation` включает документ,
приложение/пункт, таблицу при наличии и содержимое позиции, а также URL.
Порядковая строка парсера хранится отдельно как `extraction_row`: она не выдается
за официальный номер строки нормативного акта.

В `conditions.evidence[]` записаны `source_id`, `source_code`, `url`, `locator`,
`document_role`, `verification_status`, для проверенных PDF также `pdf_page`.
Сохранены исходный текст, его SHA-256, исходная ссылка и координаты извлечения.
API возвращает эти поля в `matched[].rules[].conditions`, вместе с названием
источника, URL, исходной severity и примененной `assessment_severity`.

**Техническая проверка ссылок не равна проверке истинности всех норм.**
Унаследованные таблицы имеют `extracted_not_verified`: места указаны по исходным
выгрузкам, но каждая строка не сверена заново с действующей редакцией.
`regulatory_review_report.json` перечисляет записи и основания, требующие сверки.

Обнаружены служебные заголовки, примечания об изменениях, строки «позиция исключена»
и текстовые блоки с ненадежной привязкой (например, текст приложений под заголовком
ч. 4.12). Они перенесены в `source_fragments`, не участвуют в оценке и не выдаются
за отдельные нормы с выдуманным номером пункта. При повторном импорте старые
записи с этими ID отключаются для выдачи; исходный материал хранится также
в таблице `regulatory_source_fragments` (ID, источник, исходная запись JSON).

Ниже приведено описание **исходных** файлов и счетчиков извлечения.

## Состав поставки

- `toxicheck_tr_ts_029_2012.json` — ингредиенты, синонимы и нормы безопасности из ТР ТС 029/2012.
- `toxicheck_tr_ts_022_2011_rules.json` — ингредиенты, синонимы и правила маркировки из ТР ТС 022/2011.
- `ingredient_rules_global_scope_migration.sql` — минимальное изменение схемы для правил, которые относятся ко всей продукции или категории, а не к одному ингредиенту.

Оба JSON-файла содержат массивы `regulatory_sources`, `ingredients`, `ingredient_aliases` и `ingredient_rules`. Идентификаторы созданы как стабильные UUIDv5. Для одной и той же добавки с E-кодом в обоих наборах используется одинаковый `ingredients.id`.

Счетчики и результаты проверки находятся также в объекте `validation` каждого JSON. В число правил входят и общие нормы: 1 534 для ТР ТС 029/2012 и 333 для ТР ТС 022/2011. Они сохранены в `ingredient_rules` с `ingredient_id: null`.

Большое число ингредиентов в наборе ТР ТС 029/2012 объясняется тем, что регламент содержит не только E-добавки, но и ароматические вещества, ферментные препараты, технологические вспомогательные средства и другие именованные позиции.

## Важное изменение схемы

В исходной схеме `ingredient_rules.ingredient_id` объявлен `NOT NULL`. Это не позволяет корректно сохранить общие нормы маркировки и требования к категориям продукции. Создание фиктивного ингредиента исказило бы предметную модель, поэтому миграция снимает только это ограничение и добавляет частичный индекс для глобальных правил.

## Рекомендуемый порядок импорта

1. Применить `ingredient_rules_global_scope_migration.sql`.
2. Загрузить `regulatory_sources`.
3. Выполнить upsert `ingredients` по `id` или `e_code`.
4. Загрузить `ingredient_aliases`.
5. Загрузить `ingredient_rules`.

Поле `conditions` хранит исходную строку или блок, координаты таблицы/приложения, ограничения и прочие структурированные детали. Поле `citation` содержит адресуемую ссылку на статью, пункт, приложение и строку. Значение `severity` установлено в `regulatory`: сами регламенты не присваивают медицинских уровней риска, поэтому такие уровни не были выдуманы при извлечении.

Структурированная выгрузка предназначена для загрузки и последующей предметной валидации; она не заменяет юридическую экспертизу при принятии решений о соответствии продукции.
