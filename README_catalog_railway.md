**Каталог загружен в отдельную удалённую БД Railway с полной заменой данных.**
Применена схема версии 2, журнал загрузок сохранён. Запись `catalog.import_runs.id = 2`

Количества записей во всех 19 таблицах и SHA-256 загруженного файла совпали:

Безопасная локальная пересборка и проверка, без подключения к БД:

```powershell

python -m app.db.build_catalog
python -m app.db.import_catalog ../toxicheck_catalog.json --validate-only
python -m unittest discover -s tests -p "test*catalog.py"
```

Сборщик использует текущий объединённый JSON с ручными исправлениями и сохранённую
копию `backend/db/off/ingredients.txt`. Формирует `toxicheck_catalog.json` и
`off_catalog_review_report.json`. Исходники не изменяются. `--off-input` позволяет
передать другой снимок; `--without-off` собирает только прежний справочник добавок.
Не используй вариант без OFF для замены полного каталога в БД.
В текущий отчёт добавлена отметка о подтверждённой загрузке. Повторная сборка
создаёт новый локальный снимок и сбрасывает `database_uploaded` в false:
сборщик не проверяет удалённую БД и не выполняет импорт.

## Что подготовлено

- `backend/db/schema_catalog.sql` — независимая схема справочника для PostgreSQL 16+.
- `toxicheck_catalog.json` — данные в виде массивов плоских записей, соответствующих таблицам.
- `backend/app/db/build_catalog.py` — конвертация текущего `toxicheck_proe_merged.json`.
- `backend/app/db/off_taxonomy.py` — разбор OFF, добавление ингредиентов и проверка синонимов.
- `off_catalog_review_report.json` — неоднозначные названия, коды и свойства для проверки.
- `backend/app/db/import_catalog.py` — создание схемы, проверка и импорт в одной транзакции.

Данные находятся в пространстве имён `catalog`: например, `catalog.ingredients`.
Все названия колонок английские, русские названия ингредиентов и тексты остаются
русскими значениями. Колонок JSON/JSONB и массивов в БД нет. Связи задаются UUID
и внешними ключами. Прежние UUID ингредиентов, правил и источников сохранены.
Алиасы нормализуются и дедуплицируются; спорные перемещаются в отдельную таблицу.

Исходные файлы и существующая БД не изменяются. Конвертер читает текущий
объединённый JSON, включая ручные исправления названий; старый парсер и сборщик
объединения он не запускает. Следующие ручные правки тоже нужно делать в исходном
`toxicheck_proe_merged.json`, затем повторять конвертацию.

### Что взято из OFF

Добавлены названия и синонимы на русском и английском: вода, фруктоза, молоко,
мука и другие ингредиенты. У новых записей `e_code = NULL`. Автоматических
переводов нет: 4613 узлов без русского названия сохранены в `taxonomy_entries`,
но не создают активные ингредиенты. Три узла сопоставлены с имеющимися добавками
по точному E-коду; один узел с неподдержанным кодом оставлен на проверку.

Аллергены, веганские/вегетарианские признаки, происхождение из пальмового масла,
внешние идентификаторы и другие свойства сохранены как исходные утверждения OFF
с `verification_status = reference_only`. Они **не создают правила вредности**
и не наследуются автоматически от родительских категорий.
У ингредиента может быть известное название, но отсутствовать оценка риска.
Это не означает «безопасен». Прежние 358 правил и их основания не изменились.

### Неоднозначности и будущий поиск

- 52 нормализованных названия относятся к нескольким ингредиентам. Например,
  «амарант» встречается у растения и E123; «крахмал» был синонимом разных добавок.
- Такие алиасы, несовпадающие E-коды и короткие фрагменты исключены из
  `ingredient_aliases` и сохранены в `ingredient_alias_review` с причиной.
- Будущий resolver должен искать сначала по точному `ingredients.e_code`, затем
  по `ingredient_aliases.normalized_alias`. Не обходить проверку через поиск
  `canonical_name_ru LIMIT 1` и не использовать таблицу review для автоподстановки.
- Одинаковые названия без точного E-кода не являются основанием для объединения
  с добавкой. Дополнительные сопоставления требуют ручной проверки.
- Родитель `E322i` у соевого лецитина не считается его синонимом.
- В отчёте сохранены 17 повторных блоков, 3 конфликтующих свойства и 37
  неразрешённых родительских ссылок. Неразобранных строк нет. Полный исходник
  сохранён для проверки; оригинальные переводы на остальных языках остаются в нём.

Версия схемы 2 разрешает отсутствие E-кода, добавляет таблицы происхождения
и проверки. Импортёр подготовлен к обновлению схемы 1 в той же транзакции,
что и загрузка данных. Миграция и полная замена выполнены в удалённой БД;
версия схемы, все количества записей и хеш снимка проверены отдельным подключением.

Статус находится прямо в `ingredient_rules.regulatory_status`:
`PERMITTED_WITH_CONDITIONS` (336), `BANNED` (5), `PHASE_OUT` (17).
Если правила нет, статус по имеющимся данным не установлен.
Один ингредиент может иметь несколько правил и несколько источников.
`jurisdiction` допускает NULL: территория не выводится автоматически из названия документа.

Дозировки и количественные ограничения не импортируются. Разрешение с условиями
не превращается в подтверждение соответствия конкретного продукта:
`product_compliance_assessed` всегда false. `verification_status`,
`primary_basis_required`, `production_ready` и переходные условия сохраняют
прежние оговорки о достоверности/применимости. NULL не означает подтверждение.
Регуляторный статус не является медицинской оценкой риска.

В рабочую БД не попадают русские заголовки исходных таблиц, `conditions`,
`source_fragments`, номера строк извлечения, дублированные названия из нормативной
строки, контрольные суммы текста и HTML. Исходные выгрузки остаются для сверки.
Из импортируемого каталога исключены proE как источник, его URL и предложения
в описаниях, явно ссылающиеся на этот сайт. Неизвестные источники и прямые URL
оставлены NULL; сведения не приписываются нормативным документам автоматически.
Исходные выгрузки не изменяются и остаются локально для сверки происхождения.
При последующих сборках фильтрация применяется снова. Ссылки в карточках
отделены от доказательств правил: сами по себе они не подтверждают нормативный статус.

## Создать новую БД в Railway

1. В нужном проекте Railway выбери **+ New → Database → PostgreSQL**.
   Создай отдельный сервис, например `PostgresCatalog`, и дождись его запуска.
   Старый сервис PostgreSQL оставь подключённым к работающему приложению.
2. Для загрузки с компьютера открой новый сервис: **Settings → Networking →
   Public Access**. Railway создаст TCP Proxy и переменную `DATABASE_PUBLIC_URL`.
3. В **Variables** скопируй `DATABASE_PUBLIC_URL` именно нового сервиса.
   Внутренний адрес `*.railway.internal` предназначен для сервисов Railway,
   а не для подключения с компьютера.

Эти шаги сверены с [документацией PostgreSQL Railway](https://docs.railway.com/databases/postgresql).

## Создать таблицы и загрузить данные

Ниже приведены команды для последующих загрузок. Текущий каталог уже загружен;
повторять очистку не требуется. Для локальной проверки достаточно команд в начале документа.

В терминале из корня проекта, Python 3.12+:

```powershell
cd backend
python -m pip install -e .
python -m app.db.build_catalog
python -m app.db.import_catalog ../toxicheck_catalog.json --validate-only
python -m app.db.import_catalog ../toxicheck_catalog.json --prompt-url
```

Последняя команда попросит адрес БД без отображения ввода. Вставь
`DATABASE_PUBLIC_URL` нового сервиса. Импортёр сам применит
`backend/db/schema_catalog.sql`; отдельно запускать SQL не требуется.
Пароль не записывается в исходники, JSON или историю команды.

Для автоматизации используется отдельная переменная окружения
`TOXICHECK_CATALOG_DATABASE_URL`. Без неё или `--prompt-url` импорт не начнётся.
Её также можно временно записать в локальный `backend/.env`, исключённый из Git.
Импортёр читает из этого файла только `TOXICHECK_CATALOG_DATABASE_URL`;
переменная окружения имеет приоритет. Основной `DATABASE_URL` не используется.
После сохранения URL команда работает без скрытого запроса:

```powershell
python -m app.db.import_catalog ../toxicheck_catalog.json
```

Когда временное подключение больше не нужно, удали строку
`TOXICHECK_CATALOG_DATABASE_URL` из `backend/.env`.
Если в выбранной БД уже есть `public.ingredients` прежнего приложения,
импортёр откажется её изменять.

Импорт рассчитан на **полный снимок** справочника: обновляет имеющиеся строки,
добавляет новые и удаляет отсутствующие во входном файле строки только из своих
таблиц `catalog`. Поэтому удалённые правила не остаются после повторного импорта.
Любая ошибка откатывает всю загрузку. Изменения вручную в новой БД будут заменены
следующей загрузкой; редактировать следует исходный JSON.

Для явной очистки таблиц справочника перед полной загрузкой предусмотрен
`--replace-data`. Он выполняет `TRUNCATE` всех таблиц данных `catalog` и импорт
в одной транзакции, сохраняя журнал `import_runs`. `CASCADE` не используется:
неожиданная внешняя зависимость приведёт к ошибке и откату, а не удалению чужих данных.

```powershell
python -m app.db.import_catalog ../toxicheck_catalog.json --replace-data
```

При ошибке сети проверь Public Access, хост и порт из `DATABASE_PUBLIC_URL`.
Если TCP Proxy отключить после загрузки, внешние подключения перестанут работать;
для следующего локального импорта его потребуется снова включить и проверить URL.

## Проверить результат

В SQL-клиенте, подключённом к новой БД:

```sql
SELECT count(*) FROM catalog.ingredients;       -- 1490 после загрузки версии с OFF
SELECT count(*) FROM catalog.ingredient_rules; -- 358

SELECT regulatory_status, count(*)
FROM catalog.ingredient_rules
GROUP BY regulatory_status
ORDER BY regulatory_status;

SELECT i.e_code, i.canonical_name_ru, r.regulatory_status,
       r.verification_status, r.explanation, s.title AS source_title
FROM catalog.ingredients AS i
LEFT JOIN catalog.ingredient_rules AS r ON r.ingredient_id = i.id
LEFT JOIN catalog.regulatory_sources AS s ON s.id = r.source_id
WHERE i.e_code = 'E330';

SELECT * FROM catalog.import_runs ORDER BY id DESC LIMIT 5;
```

Если нужна только пустая схема, её можно применить через `psql` с параметрами
нового сервиса. Команда из корня проекта, пароль вводится отдельно:

```powershell
psql -h HOST -p PORT -U USER -d DATABASE -W -v ON_ERROR_STOP=1 --single-transaction -f backend/db/schema_catalog.sql
```

## Подключение приложения

Эта схема обслуживает справочник ингредиентов. Таблицы пользователей, сканирований,
оплаты и другие прикладные таблицы в неё не переносятся.
Код backend адаптирован к схеме `catalog`, версия 2. Анализ, поиск ингредиентов,
каталог предпочтений и `/api/health/db` используют отдельное подключение только
для чтения. `conditions` в ответах API собирается из плоских правил, `rule_evidence`
и `rule_transitions`, без обращения к старым JSONB-таблицам. Наличие правила
разрешения не означает подтверждённую безопасность; отсутствие правил даёт
`severity = unknown`. Точный поиск не использует нечёткие совпадения и review-алиасы.
Старые UUID исключений сопоставляются через `ingredient_matches`; прежние строковые
ID через записи `source = legacy_preference_id` (включая архив review исключительно
для миграции явно выбранных пользователем ID, не для распознавания состава).

Для выкладки обновлённого кода добавь у сервиса backend:

```env
TOXICHECK_CATALOG_DATABASE_URL=${{Postgres-hcbk.DATABASE_URL}}
```

Имя сервиса должно совпадать с фактическим. Если эта переменная пуста, используется
`DATABASE_URL`, который в таком случае должен указывать на каталог. При отдельных
БД старый `DATABASE_URL` можно оставить для будущего прикладного хранения.
Для локального запуска применяется public URL из игнорируемого `backend/.env`.
Новая БД не должна получать старый `app.db.apply_schema`/`import_regulatory_data`.
Старый pre-deploy удалён из `railway.json`; убери его также в Railway Settings,
если он был задан вручную. Затем выполни деплой backend и frontend.
Само изменение исходников не обновляет уже работающие экземпляры Railway/Vercel.

Проверка `/api/health/db` должна вернуть HTTP 200, `schema = catalog`,
`schema_version = 2`. Отсутствующая, пустая или несовместимая схема даёт HTTP 503,
без выдачи пароля и строки подключения. Результат скана штрихкода и очищенный
результат OCR попадают в один и тот же анализатор нового каталога.

Синтаксис описан в [Railway Variables](https://docs.railway.com/variables).

## Проверки разработки

```powershell
cd backend
python -m unittest discover -s tests -p "test*catalog.py"
```

По умолчанию запускаются проверки конвертации, интеграционный тест пропускается.
Для проверки SQL и импорта в отдельном временном PostgreSQL:

```powershell
$env:TOXICHECK_TEST_POSTGRES_BIN = 'C:\Program Files\PostgreSQL\16\bin'
python -m unittest discover -s tests -p test_catalog.py
Remove-Item Env:TOXICHECK_TEST_POSTGRES_BIN
```

Тест создаёт собственный временный кластер, слушающий только `127.0.0.1`,
проверяет повторный импорт, удаление устаревшего правила и откат ошибки,
затем останавливает сервер и удаляет временные файлы. Существующие БД не используются.
